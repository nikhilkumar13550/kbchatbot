What the MVP is

EHC/Drug tabs only. 12 Policy App tabs and 611 fields. All other benefit tabs (Life, AD&D, Disability, Dental, Critical Illness, spending accounts, etc.) are later phases.

Mapping first. Connect selected Policy App data entry points to where each value lives downstream (system, screen, field, or document), then compare and flag mismatches for an auditor to review.

Why EHC/Drug. The write-off analysis identified Drugs as the highest-risk area. Starting here keeps the MVP manageable while proving an approach that can expand to other benefits.

Read-only. The QC tool flags discrepancies; it does not correct source systems, contracts, or booklets.

How these numbers are worked out

  • Status comes only from the System / Mapping Status block at the top of each tab in Policy App Mapping to Systems.xlsx — not from tab colours or my interpretation.
  • Data elements are counted once per Policy App source cell on each tab (612 across the 12 MVP tabs), so a cell mapped to several systems is counted once.
  • 611 vs 612: 611 is the fillable-field count from the MVP Overview audit (used for scope percentages); 612 is the number of source cells listed in the mapping tabs (used for progress). They differ slightly because mapping splits or adds a few cells — e.g. EHCOOC lists 22 cells against 21 fillable fields.
  • "Done" for a system = Complete or Not required. A tab is Complete for V3/ESC/CPM when all three are done; Pending validation when the rest is done but one says "completed first round, pending validation".
  • Open items = field-table lines that still say "Needs SME validation", "Not validated", "Needs further review", "verification" or "TBD", plus any status that contradicts the field table (e.g. "Not required" with mappings recorded).

Headline: this is not field-to-field mapping

Every session reached the same conclusion — Policy App values don't map one-to-one to a downstream field. The QC tool has to handle several kinds of relationship:

Directone Policy App value → one downstream field
Derivedseveral values combine to pick one code (GS Code, Travel Assist ID)
One-to-manyone value creates several records (visit count + dollar max)
Guidingtells the coder what to do but isn't stored itself
Expected absencean excluded service correctly has no record
Commentsexceptions live in free-text Additional Comments
Lookup tablescodes come from an external table (ETA Plan ID, Travel Assist ID)
Wording presencein the contract, whole lines or paragraphs are kept, marked "not covered" or deleted

ManuConnect mapping sessions

ManuConnect 1All EHC tabs → ManuConnectOct 22, 2026

SME: Sherri Holt · Target: Client Maintenance › Plans Offered › Plan Benefit Basic / Plan Benefit Option

Key findings

  • ManuConnect is a small, low-complexity target. Most EHC and drug plan design (deductibles, maximums, reimbursement, sliding scale) lives in ESC and claims systems, not MC.
  • Fields split and combine: waiting period becomes four MC fields; dependent definition becomes min/max age; two survivor extension fields become one.
  • Terminology differs ("present/future" in the Policy App = "current/new" in MC), and flex option names are inconsistent (01 / one / gold) — needs normalization.
  • Out of Country ETA Plan ID and Service Code come from an external lookup table.
  • Real-world evidence: an external auditor found hospital co-insurance missing from a contract and booklet that morning — "This tool probably would have caught it."
  • Agreed out of MVP scope: rates (billing only), PPN, claims paying office.

Contract mapping sessions

Contract 2EHC Drug → contractOct 22, 2026

SME: Jeff Jones · Targets: Group Benefit Schedule, Extended Health Care drug benefit, Policy Addendum

Key findings

  • EHC Drug and EHC Drug Custom map identically — map once and copy.
  • Standard values usually mean no contract change; non-standard values trigger a targeted edit. QC must check both that text appears and that it doesn't.
  • Many fields roll into one line: Benefit Percentage (tier %, sliding scale, split brand/generic, dispensing-fee coinsurance) and eight maximum fields into "All other covered drug expenses".
  • Generic substitution wording is swapped wholesale from three model versions; a provincial formulary replaces the tier drug plan in both schedule and body.
  • 9+ drug fields are administrative only (e.g. DIN, Prior Authorization, Virtual Pharmacy) and should be tagged "Not contractualized".
  • Known audit exposure: preventative items coded "No" must be deleted from one section and added to the not-covered list.
Contract 1EHC & Orthopaedic → contractOct 20, 2026

SME: Jeff Jones · Targets: Group Benefits Schedule, Definitions, Extended Health Care benefit wording

Key findings

  • Policy App-to-contract QC is viable. Contracts are drafted from standard models, so wording outside the variables stays the same.
  • QC has to check that wording is present, marked "not covered", or removed — not just that values match.
  • Coverage is judged across all plans: if no plan covers a benefit the line is deleted; if some do, the line stays with "not covered" for the others.
  • Several fields combine into one sentence (termination age; overall maximum), and some fields appear in two places (Survivor Extended).
  • "Deductible applies" works by exception — the contract states the default and only lists what the deductible does not apply to.
  • Unresolved: retiree accumulation and maximum-reset wording. Drugs and Professional Services are expected to be more complex.

System mapping sessions (V3, ESC, CPM)

Session 5PPN & EHC Drug Step TherapyOct 15, 2026

Primary systems: ESC (GS Profile / Group Profile, GSAS), CPM

Key findings

  • Preferred Provider (PPN) proposed out of scope — set-up varies by pharmacy, chain and location, needs dedicated ESC benefit codes, and relies heavily on Additional Comments and supporting documents.
  • Step Therapy is a stronger candidate for rule-driven QC: it can be set at group or plan level, with drug modules, provinces and effective dates each creating records.
  • Standard cognitive-fee treatment means no GSAS override; non-standard needs a GSAS exception plus a QMID from separate reference data.
  • CPM holds relatively clear Step Therapy indicators (sold? Plan Member Guide applies?).
  • "Overall EHC deductible applies" is a routing rule — Yes means inherit the EHC set-up, No means code a separate drug deductible.
Session 4Out of Country (EHCOOC)Oct 14, 2026

Primary system: V3 (Parameters, Limits, Benefits, Categories/TOSS)

Key findings

  • Travel Assist ID is derived from several Policy App answers — and was in the input file but not visible in the V3 screens reviewed.
  • Referral and emergency coverage need separate TOSS/category set-ups with their own coinsurance, maximum and period.
  • Standard service codes are defaulted; deviations come through Additional Comments.
  • Trip-duration options are mutually exclusive — a clean, automatable source-validation rule.
Session 3Professional Services (EHCProfServ)Oct 13, 2026

Primary system: V3 (Payments, Limits, Set up / Rule Sets); one CPM brochure item

Key findings

  • V3 / data lake configuration — not the coding input file — should be the QC comparison point.
  • ~130 entry points may collapse into ~10 reusable V3 patterns; a strong candidate for a reusable mapping template.
  • Combined maximums, visit count vs. dollar max, and initial vs. subsequent visits each need relationship-level checks.
  • "No downstream record" can be the correct result for excluded or guiding fields.
Session 2EHC & EHC DrugOct 8, 2026

Primary systems: ESC, V3, CPM

Key findings

  • Sliding coinsurance is a composite rule (rate, breakpoint, type, applicability work together).
  • Some Policy App fields are instructions to the coder, not stored values.
  • Standard vs. non-standard drives everything — exceptions are deviations from a standard plan.
  • QC must check maximum placement and basis, not just the amount.
Session 1EHC Drug, General EHC, EHC HospitalDate not recorded

Primary systems: ESC (GS Profile, GS Code, Benefit Parameter Table, LDF, SDC), V3

Key findings

  • Drug-plan / GS Code selection is derived from several Policy App values.
  • Brand vs. generic is embedded in the GS Code format (a "G" prefix = generic).
  • Drug deductible can inherit the overall EHC deductible — a cross-tab dependency.
  • Province (RAMQ, formulary, SDC, LDF) materially changes configuration.
